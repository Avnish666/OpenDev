# Phase 5 Step 3: financial accountability reasoning

**Deployment remains NO-GO.** This extends the existing single public read-only
agent; no second agent, dependency, financial persistence, migration, frontend UI,
paid API, approval action, commit, push or deployment is introduced. Uncommitted
Step 2 work is preserved.

## Architecture and source of truth

New `backend/app/agent/financial_reasoning.py` provides strict financial claim
plans and server-owned explanation templates. `answers.py` extends deterministic
intent aliases; `orchestration.py` extends the existing prompt, tool descriptions
and grounded-answer validator. The same dispatcher, provider adapters, snapshot,
visibility checks, body/rate/concurrency limits, timeouts and context budgets apply.
No new response fields are needed, and all three execution modes remain compatible.
`execution_mode` reports actual use; fallback remains explicitly labeled.

The seven-tool allowlist is unchanged. No specialized tools are necessary:

| Existing tool | Financial evidence used |
| --- | --- |
| get_project_finances(project_id) | PublicTransparency: reconciliation, budget variance, public document coverage, published category-overrun findings, accounting notes |
| get_project_expenses(project_id, offset=0) | Published LedgerPage: expense IDs, reported amounts/dates, approved-redaction metadata and public category findings; 50 entries/page |
| get_project_overview(project_id) | Existing project identity, funding goal and currency; remains available for LLM scalar selections |

Both financial tools enforce active public project visibility even for the owner.
The server pins dispatch to the request's authorized project ID. No tool calls
private verification, extraction, review, original download or payment endpoints.

All monetary totals and comparisons come unchanged from:
`transparency.overview` → `accountability.snapshot(db, project, None)`.
`transparency.ledger` remains the source for public expense/document lists. This
step does not rescan Contribution/Expense tables or implement another accounting
formula. It only formats the authoritative integer values and selects category
rows. Amounts are displayed in recorded currency minor units, without floating
point, exchange rates or inferred percentages.

The existing snapshot provides:

- Gross completed captured funding, including captures now refunded/reversed.
- Original capture amounts conservatively excluded for refunds and reversals.
- Net eligible completed funding, published reported spending, and their calculated
  difference. The difference is explicitly **not a verified cash/bank balance**.
- Category allocations, reported spending, remaining allocation and overrun.
- Supported/unsupported public expense counts and amounts, counting each expense
  once regardless of multiple documents, extraction versions or attempts.
- Public unresolved category-overrun findings; private discrepancy counts remain
  withheld/null rather than represented as zero.

Pending/failed/uncaptured contributions and unpublished expenses retain the existing
exclusions. Capture/event uniqueness and conservative partial-refund treatment are
unchanged. **Refund exclusions are not exact refund amounts.** Partial refund
amounts are not stored; a partly refunded capture is excluded entirely, and the
agent explicitly says the exact amount refunded is unavailable.

## Verified financial claim plans

The model still dynamically selects tools and may use Step 2 scalar `facts`.
For common financial relationships it can instead return:

```json
{
  "financial_claims": [
    {
      "kind": "funding_reconciliation",
      "references": ["<exact current finance citation.reference>"]
    },
    {
      "kind": "expense_support",
      "references": ["<finance citation.reference>", "<expense-page citation.reference>"]
    }
  ]
}
```

Allowed kinds: `funding_reconciliation`, `refunds`, `budget_variance`,
`expense_support`, `public_findings`, `consistency`, `missing_information`,
`reporting_changes`. Up to six claims/plan; each requires exactly one retrieved
finance citation. Support/consistency also require expense-page citations.
Budget variance may specify an optional exact existing `category`; nonexistent
categories are rejected. Extra keys, model amounts, converted currencies,
percentages, explanations, accusations and mixed facts/financial_claims output
are rejected. Values and relationship wording are generated by trusted templates,
not accepted as model assertions. Rejected model output triggers the existing
bounded deterministic fallback or explicit insufficient evidence.

Every reference must be present in this request's evidence registry, match public
visibility and the same project, and refer to the required source kind. A private,
invented, historical or unrelated citation cannot license a financial claim. Both
summary and ledger are retrieved inside one read-only repeatable-read transaction.
Ledger currency/project mismatches are rejected rather than converted. Complete
financial templates make net/gross/spending distinctions explicit, preventing
model-supplied contradictory totals or bank-balance claims. Final answer text
still obeys the configured maximum; oversized explanations return constrained
insufficient evidence rather than silently truncating a financial claim.

Each paragraph includes its source citations. Existing stable source IDs, full
public projection hashes and paths are preserved. Only used envelopes are returned;
source freshness, retrieval time, last-update information and accounting limitations
are retained. Snapshot calculation time is not independently verified settlement
or a historical reporting date.

**Citation existence alone is not semantic proof.** Models can choose irrelevant
or incomplete templates. Public source text is untrusted reported data, not verified
truth. Templates constrain relationships and prohibit free-form causal conclusions;
they do not prove completeness, authenticity, intent, vendor payment or causation.
No claim of fraud or personal dishonesty is generated. This is not a financial
audit, fraud detector, payment decision engine or automatic approval system.

## Supported questions and evidence gaps

Deterministic mode recognizes exact intent keys and normalized documented phrases,
not arbitrary semantic paraphrases. Added phrases include:

- “How much has been refunded?” (`refunds`)
- “How much has the maintainer reported spending?” (existing `spending`)
- “Which budget categories are over budget?” (`budget_variance`)
- “Is this project spending more on infrastructure than planned?” (same intent;
  explicitly selects infrastructure, or says evidence is insufficient if absent)
- “Which published expenses lack supporting documents?” (`expense_support`)
- “What discrepancies have been publicly disclosed?” (`public_findings`)
- “How much recorded funding remains after reported expenses?” and
  “Why is the project running out of funds?” (`funding_reconciliation`)
- “Are expense reports consistent with approved supporting evidence?” (`consistency`)
- “What financial information is missing?” (`missing_information`)
- “What changed between available reporting dates?” (`reporting_changes`)

Existing funding, spending, categories and nonfinancial Step 1 intents still work.
LLM mode can select templates/tools for other phrasings, subject to validation.
A funding-gap answer reports reconciliation and disclaims its cause; it cannot
explain maintainer motives or undocumented spending decisions.

Expense support answers distinguish no **approved public** document support from
attached approved-redacted documents; private support may exist. Global coverage
amounts/counts come from the full summary. Listed unsupported expense IDs cover
only retrieved ledger pages, with explicit paging limitations; absent IDs on a
page do not establish global absence. The model can retrieve additional bounded
offsets under the unchanged six-tool-call/three-turn defaults.

Current publication policy does **not** approve publication of extraction-consistent,
private receipt mismatch, or human-review states. Approval of a redaction does not
publish its original's OCR. Public discrepancy answers therefore discuss only
published category totals, not private receipt findings. Consistency answers are
explicitly `insufficient_evidence`, even with an approved attachment. No independent
payment-matching channel exists; attaching a receipt never certifies vendor payment.

Historical financial snapshots are not persisted. Current expense dates/update
timestamps cannot reconstruct earlier contribution states, budgets or edited
reports. Reporting-change answers return `insufficient_evidence` with the current
snapshot citation rather than fabricate historical amounts. Exact partial refunds,
independent bank balances, hidden receipt findings and complete external spending
are likewise missing evidence, not quantities the agent guesses.

## Evaluation and tests

`backend/tests/data/financial_agent_evaluation.json` is a reproducible 15-case
question/answer dataset with synthetic fixture seeds, expected authoritative fields,
required source kinds, expected answer excerpts and statuses. The test runner also
enforces forbidden affirmative claims, recomputes citation SHA-256 values, checks
project scope and tests private identifier/key/notes exclusion. These are synthetic
contract evaluations, not a real-world accuracy percentage.

Cases cover fully/partially/no recorded funding, reported spending, no public
support, multiple documents, over/under-budget categories, public/private findings,
refund/reversal exclusions, consistency limitations, missing data, unavailable
reporting history and constrained causal questions. Additional tests cover actual
mocked three-turn finance+expense orchestration, fabricated amounts/currency/
percentages/causes/fraud, foreign citations, deterministic fallback, unavailable
sources, paging, active/draft privacy, duplicate capture/webhook constraints,
unchanged financial rows, infrastructure comparisons, partial-refund disclosure,
empty projects, and extraction versions/attempts without double counting.
A SQL observer verifies public reasoning never queries private extraction/attempt/
review tables. Earlier tests retain readonly SQL rejection and provider-limit coverage.

Automated tests use mocked models and real isolated local PostgreSQL. Live Ollama
inference **was not run**. Step 2's catalog-access and GPU limitations remain; no
new model/version/VRAM claim is made by Step 3. No frontend UI or ledger duplication
was needed, but all frontend compatibility checks are run.

```sh
curl -H 'Content-Type: application/json' \
  -d '{"project_id":42,"question":"How much recorded funding remains after reported expenses?","mode":"deterministic"}' \
  http://localhost:8000/api/projects/42/agent/query
```

Compare returned fields/citations to `/api/projects/42/transparency` and `/ledger`.
Use synthetic refund/reversal states and multiple approved redactions; compare
anonymous and owner responses and confirm no private receipt IDs/notes appear.
Query consistency and historical changes; both must acknowledge insufficient
public evidence. From frontend/: `npm test`, `npx tsc -b`, `npm run build`, `npm run lint`.

`phase5-agent-orchestration.md`, optionally run from backend/:

```sh

  --question 'Compare recorded funding and approved public expense support.'
```

Require actual execution_mode=llm, examine citations/limitations, and compare
minor-unit amounts to the deterministic API. A fallback is not proof of live LLM
reasoning. Do not expose unauthenticated Ollama publicly or assume cloud localhost
